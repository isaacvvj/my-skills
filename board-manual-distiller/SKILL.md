# 板卡手册与引脚资料蒸馏器（board-manual-distiller）

将 MCU 开发板/芯片的数据手册、原理图、引脚图、Wiki 等资料蒸馏为**可检索、可链接、可追溯**的结构化 Markdown 档案，适用于 Obsidian 知识库管理。

## 何时使用

当用户出现以下需求时**必须**调用本技能：
- "把XX开发板的资料整理一下"
- "蒸馏XX芯片手册成md文件"
- "做一个XX的引脚速查表"
- "整理硬件资料方便管理"
- "把这个板卡的资料做成知识库笔记"
- "帮我把XX的手册资料归档"
- 提到"板卡档案"、"引脚定义"、"PinMux"、"资料蒸馏"、"硬件知识库"等关键词

## 输出结构

采用"**主档案 + 芯片级PinMux + 板级接口**"的三层结构：

```
目标目录/
├── <板卡名><芯片型号>开发板档案.md      # 主索引：身份、资源概览、资料入口、导航
├── <芯片型号>-芯片资源与PinMux速查.md    # 芯片层：外设、引脚复用、电气特性
└── <板卡名>-板级引脚与接口.md          # 板卡层：排针/丝印/板载外设（有原理图时创建）
```

### 可选补充
- `<板卡名>-供电调试与启动.md` - 供电设计、调试技巧、启动模式详解
- `芯片与开发板资料索引.md` - 多块板卡的总索引目录（批量蒸馏时必建）

## 蒸馏原则（每一条硬件事实必须回答）

**是什么、适用于什么、来自哪里、可信状态是什么。**

### 状态分级
| 状态 | 含义 |
|---|---|
| 手册已确认 | 官方文档明确描述的规格 |
| 原理图已确认 | 原理图明确标出的连接 |
| 项目已使用 | 当前工程有对应配置 |
| 已上板验证 | 有实物测试记录 |
| 待确认 | 无法由可信来源确认 |
| 冲突待处理 | 不同资料结论不一致 |

### 可信等级（trust_level）
- **L0**：官方手册、原理图、网络资料（默认起点）
- **L1**：本机构建/静态配置/EDA检查通过
- **L2**：目标板上完成功能验证
- **L3**：多项目稳定复用，有故障记录

> 默认从 L0 开始，不要因单个功能验证就整体升级。
> 文件头部 YAML 中的 `trust_level` 与表格中的"状态"列要严格区分使用。

## 工作流程

### 第一步：资料盘点（只读）
1. 明确目标：芯片型号 + 具体板卡名称 + 封装
2. 定位资料来源：官方数据手册、参考手册、开发板Wiki、开源硬件原理图、BOM表
3. 评估资料完整性，标记已知和未知
4. 用 WebSearch/WebFetch 收集资料，**优先官方来源**

### 第二步：芯片级蒸馏
1. 核心规格（主频、Flash、RAM、封装选项）
2. 外设资源清单（UART/I2C/SPI/ADC/TIM等数量）
3. 引脚分配参考（按端口整理，标注主要复用功能）
4. 时钟、调试、电气特性
5. 不同封装的差异对比

### 第三步：板级蒸馏
1. 板载资源盘点（LED、按键、串口、Flash、传感器等）
2. 供电系统（输入电压、稳压方案、保护电路）
3. 调试接口与启动方式
4. 板级引脚占用情况
5. 已知限制和注意事项

### 第四步：索引与链接
1. 主档案链接到各专题笔记
2. 专题笔记互链
3. 所有关键事实附来源
4. 未知项统一进"待确认"

## 信息来源优先级

| 优先级 | 来源 | 用途 |
|---|---|---|
| 1 | **官方数据手册/参考手册** | 芯片级事实的最高依据 |
| 2 | **官方开发板Wiki/用户手册** | 板级连接的权威来源 |
| 3 | **开源硬件原理图/BOM** | 板级电路的直接证据 |
| 4 | **官方产品页** | 规格参数的补充 |
| 5 | **社区/博客资料** | 仅作参考，需交叉验证 |
| 6 | **实物测量** | 最高等级（L2/L3） |

## 多来源交叉验证方法

当不同来源对同一事实描述不一致时：
1. **官方手册优先**：数据手册 > Wiki > 社区
2. **标注冲突**：在"待确认与冲突"章节标注"冲突待处理"，列出各来源的说法
3. **保守取值**：电压、电流等电气参数取更保守的值
4. **不猜测**：无法确认时写"待确认"，不要用"可能是""大概是"

## 强制约束

- ❌ 不从记忆或网络猜测引脚、电平、供电
- ❌ 不把手册/原理图写成上板验证
- ❌ 不编造不存在的外设或引脚
- ❌ 不把整篇笔记因某个功能验证就整体升级trust_level
- ✅ 每个关键结论附 source_path 与 版本/页码/章节
- ✅ 冲突资料明确标注"冲突待处理"
- ✅ 未知项写"待确认"，不猜测补全
- ✅ YAML frontmatter 规范、可解析
- ✅ 网络引用使用 `[$TRAE_REF](url)` 格式，本地资料在"资料来源"章节列路径

## 多板卡批量处理

处理多块板卡时：
1. 同芯片的不同开发板共享一份芯片级PinMux笔记
2. 每块开发板有独立的主档案和板级接口笔记
3. 创建一份总索引（`芯片与开发板资料索引.md`）
4. 各笔记之间通过 Obsidian `[[]]` 链接互相关联
5. 批量处理时先建好 todo 列表跟踪进度，逐块完成

## 常见问题排查

| 问题 | 处理方式 |
|---|---|
| 找不到官方数据手册 | 使用Wiki/产品页作为替代，明确标注来源降级 |
| 原理图不完整 | 使用BOM表补充，引脚连接标"待确认" |
| 芯片有多个封装变体 | 分别列出封装差异，标注对应开发板 |
| 社区资料与官方冲突 | 以官方为准，冲突进"待确认与冲突" |
| 引脚功能过时/更新 | 标注数据手册版本，注明需以最新版本为准 |
| 用户给了本地PDF/图片 | 用local-mineru/pdf等工具解析后蒸馏 |
| 板级信息完全缺失 | 只创建主档案+芯片级笔记，板级笔记标"待创建" |
